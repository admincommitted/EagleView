EagleView EDI: how the project fits together

A map of the two folders you will work in (frontend and node-backend), the database behind them, how login and rights work, what the masters are, and where to look when something breaks. Row counts are from your live database.sqlite.

Big picture

There are three programs running. The frontend is a React app (Vite) that runs in the browser on port 5173. Every screen talks to the backend, an Express server on port 5001, by calling URLs that start with /api/…. The backend reads and writes one SQLite file, node-backend/database.sqlite, through Sequelize (the ORM). A separate DSC Signer on port 5050 signs files with the USB token before they go to ICEGATE.

Folders you will work in

frontend/src

  • main.jsx: starts the app. It also adds the login token and the branch / FY headers to every /api call, and sends you to /login on a 401.
  • App.jsx: the URL → screen list (about 75 routes).
  • GlobalContext.jsx: the selected branch and financial year from the top bar.
  • layouts/MainLayout.jsx: the menu, top bar and page frame.
  • pages/ (102 files): full screens like Dashboard, Accounts, Reports.
  • components/JobEntry (69): Import / Bill of Entry screens.
  • components/ExportEntry (53): Export / Shipping Bill screens.
  • components/FreightForwarding (104): AWB, MAWB, HAWB, shipments.
  • components/MDMForms (54): all master forms.
  • components/Settings (28): settings screens.

node-backend

  • server.js: starts Express, loads all models, links tables (associations), and mounts every route under /api/….
  • db.js: opens SQLite (or MS SQL when DB_DIALECT=mssql).
  • .env: secrets and settings (JWT secret, SMTP, ICEGATE, DB).
  • models/ (138 files): one file per table definition.
  • routes/ (66 files): the API code each screen calls.
  • middleware/auth.js: checks the login token.
  • middleware/permissions.js: checks the user's module rights.
  • utils/ (64): shared logic (numbering, branch scope, ICEGATE, columns).
  • uploads/: saved files. You need to be logged in to open them.
  • fix_*.js, load_*.js, seed_*.cjs: one-off data scripts. They change the database.

Login & rights: what happens on every request

The login screen sends the User ID and password. The backend finds the user in Users (the User ID is case-insensitive, and the e-mail also works), checks the bcrypt password hash and returns a JWT token. The browser keeps that token in localStorage and sends it with every call after that.

  A->>DB: find user (lower(username) or email)
  A->>A: status active? bcrypt.compare(password)
  alt login from outside the office and OTP is on
    A-->>L: e-mail OTP, then POST /api/auth/login/otp
  end
  A-->>L: token (id, username, role) + module rights
  Note over L: saved in localStorage "token"

  L->>A: any /api call with "Authorization: Bearer token"
+ X-Branch + X-FY headers

The checks every /api call passes through (in server.js order)

  1. Open routes: /api/auth/* (login, forgot / reset password) and /api/field-tracking need no token. Signed PO and KYC links from e-mail also work without one.
  2. middleware/auth.js checks the token is valid and not logged out, and that the user still exists and is not inactive or locked. If any of that fails, the call gets a 401 and the screen goes to the login page.
  3. middleware/permissions.js checks module rights:
    • The role admin is allowed everything.
    • A user with no rows in UserPermissions is also allowed everything, except changing System Settings and User Management.
    • Otherwise the URL is mapped to a module, and the HTTP method decides which right is needed: GET → canView, POST → canCreate, PUT → canEdit, DELETE → canDelete.
  4. utils/branchScope.js (accounts, vouchers, invoices, reports, credit control only) limits the data to the branch picked in the top bar.
  5. Then the route file does the real work through the models.

The token lasts 1 day (10 hours from outside the office). Logout cancels it on the server at once.

Found while reading: UserPermissions has 30 rows, but every one has an empty userId. They belong to no user, so they have no effect. They are probably left over from a user that was deleted or never saved properly. This is harmless, but it is worth cleaning up later.

Masters: the lookup data every job uses

A master is reference data you pick from in a form: party, port, currency, HS code and so on. You manage them on the /master/* screens (components/MDMForms). Most go through /api/masters (routes/masters.js); some have their own route (/api/locations, /api/tariff, /api/tact, /api/masters/ports). A lot of this data was imported from the old software (iCAFFE / Logisys) with the load_*.js scripts.

Jobs and accounts: where the daily work is saved

Import (Bill of Entry)

Screens /job-entry/* → API /api/import-jobs (routes/importJobs.js).

ImportJobs 4,148 → ImportInvoices 6,299 → ImportItems 78,477. Also ImportContainers. A job points to its parties with importerPartyId, supplierPartyId, notifyPartyId and buyerPartyId.

From here it goes to ICEGATE: the BE JSON is built, signed by the DSC Signer and uploaded (routes/icegate.js). The documents go through e-Sanchit.

Export (Shipping Bill)

Screens /export-entry/* → API /api/export-jobs.

ExportJobs → ExportInvoices → ExportItems. Also containers, documents, drawback lines and licences. A job points to shipperId, consigneeId, branchId and financialYearId.

Freight forwarding

Screens /freight/* → /api/awb and /api/shipments.

Airwaybills / MasterAWBs / HouseAWBs share child tables (dimensions, rate lines, other charges, SHC, OCI). Each child row stores awbId plus awbType (AWB / MAWB / HAWB), so it is not a normal foreign key. Shipments has 12,130 rows.

Accounts

Screens /accounts-hub, /voucher-entry, reports → /api/accounts-hub, /api/vouchers, /api/invoices.

AccountGroups 180 (a tree) → AccountLedgers 7,663. Vouchers 326,163 → VoucherDetails 4,248,442 (one debit / credit line per ledger). VoucherTypes lists Sales, Purchase, Payment, Receipt, Journal and so on. Sales bills are in AccSalesInvoices (116,605).

Smaller modules: Sales / CRM (Leads → Quotations → QuotationCharges), Purchase (Vendors → PurchaseOrders → POItems), Fleet (LorryReceipts), Field tracking (FieldAgents, locations), Contracts.

Solid lines are links by id. The dotted line is a link by matching text: a voucher or sales invoice knows its job only through the jobNo string, and its branch through branchCode. So if a job number is changed, its bills no longer find it.

Two things that surprise people: (1) Only about 138 of the 202 tables have a model file. The others (most Acc* and Icaffe* tables) are created by plain SQL inside the route files, so search routes/ for CREATE TABLE to find them. (2) Columns are added automatically at start-up (utils/ensureColumns.js, utils/dynamicColumns.js), which is why ImportJobs has 247 columns and ExportJobs has 193. Extra form fields that have no column yet are kept as JSON in extendedData.

Debug cheat sheet: from a screen to the code

  1. On the broken screen, press F12 → Network and repeat the action. Find the red or failing /api/… call and read its Response.
  2. Take the first part of the URL (for example /api/import-jobs) and find it in node-backend/server.js (the app.use('/api/…', require('./routes/…')) lines). That tells you the route file.
  3. In the route file, search for the rest of the path (router.get('/:id'…). That is the code that ran.
  4. Look at the backend window. Server errors are printed there with a reference like [API LX3K9], and the screen shows the same reference.
  5. Check the data in DB Browser (open it Read Only while the backend runs): the table name is the model name plus "s", for example ImportJob → ImportJobs.
